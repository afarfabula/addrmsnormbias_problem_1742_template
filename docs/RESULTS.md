## v7（已提交 a4e88d6，已推送）— fp16/bf16 小 D 批量 pass2 + repeat 批量归约 + 超宽行窗口化
- 内容：
  - **批量 WholeReduceSum**：每 tile 128 次独立 64->1 硬件归约合成一次
    `repeat=g` 的指令（实测该归约在 c220 把每行结果写到**连续**元素，非 8-lane 间隔）；
  - **fp16/bf16 D<=384 对齐行批量 pass2**：γ/β 在 Init 复制成整 tile（fp32 行内复制），
    rstd 用 Gather（offset 单位为**字节**）在 vector 域展开，替代每行 GetValue +
    逐行 Muls/FMA/Cast（旧路径 ~4 短向量指令/行 → ~5 条整 tile 大向量指令）；
    tile 上限 6144 元素（D=64 -> 96 行/tile）。
  - **超宽对齐行窗口化（group 内 ultra_）**：fp16/bf16 D>8192、fp32 D>4096（上限
    32768/16384）时，按 GT_ELEMS 宽窗口两次读 x/residual：pass1 逐窗口折 sq 进
    64-lane acc -> rstd；pass2 逐窗口重读并按 PARAM_STRIPE 应用 γ/β。
  - host 对齐 gate 上限提升：fp16/bf16 D<=32768、fp32 D<=16384。
- 精度：`run_accuracy.py` 16/16 ALL PASSED；`run_heavy_accuracy.py` 13/13 PASS；
  超宽行独立 8 组（fp16 D=16384/32768、fp32 D=8192/16384 × 多行数）vs golden 全 PASS。
- msprof（310B, dev_avg, reps=300）：
  - 4M 行 x D=64 fp16（[2048,2048,64]）：Task 10.5ms -> **4.12ms**；aiv_vec 0.50 /
    scalar 0.41 / mte2 0.12 / mte3 0.06（优化前 vec 0.71+scalar 0.47 的逐行短指令+标量读

## (v14 实验期 2026-09-09) — 三路候选改造的本地测量与结论（未合入）
- 背景：官方 v12=39.56/#11-272µs/#13-776µs 后，测试了 ①PadWide 单读 y-hold、②PadWide 块级
  两阶段 UltraPadAll、③微 case 小行数路由，全部**未达合入标准**，kernel 保持 v13 原样。
- ① 单读 y-hold（fp16 行 y 以 fp16 常驻 64KB / fp32 128KB，pass2 不回读 GM x/residual）：
  - 精度：fp32/fp16 非对齐宽行 vs numpy golden 全 PASS（fp32 maxdiff 9.5e-7、fp16 2.0e-3，
    bf16 为既有 ~2ULP 量级差异）；但行尾 γ 非对齐 DataCopy 会错最后 4 列（已定位修复）。
  - 性能（v13 per-row -> hold）：fp16 [1024,32760] 368→370（≈）、[2048,32760] 747→777（≈）；
    fp32 [512,32764] 240→404（+68%）、[1536,32764] 797→1404（+76%）——fp32 反而显著回退。

    UB 内 y 往返与更小窗口的向量/同步开销吃掉收益。
  - 另注意：历史 v9 记录曾提示 fp16 y 缓存会让 ~0.7% 元素超 1e-3 官方阈值（vs torch golden），
    本方案精度上也有同类风险 → **弃用**。
- ② PadWide 块级两阶段 UltraPadAll（行密集 G=8：pass1 逐行 WholeReduceSum->sum_[r]，整块批量
  rstd 一次 V_S/S2V；pass2 列 stripe(2048) 外循环/行内扫、γ/β 每 stripe 块内只读一次）：
  - 精度：fp16/fp32/bf16 宽行专项全 PASS（与 v13 逐位一致量级）。
  - 性能（v13 per-row -> UltraPadAll）：fp16 [512,32760] 186→185（≈）、[1024] 368→384（+4%）、
    [2048,32760] 747→865（**+16% 回退**）；fp32 [512,32764] 240→210（-12%）、[1024] 547→588、
    [1536] 797→861、[2048] 1064→1149（+8%）。
  - 与 group1 对齐 UltraAll（v9，对齐宽行 -13~22%）结论相反：pad 宽行 stripe-outer 行扫把每行
    读切成多个 2048 段、跨 40 核交错，破坏了大行连续读的 GM 局部性；fp32[512] 的 -12% 是少数
    例外 → **弃用，kernel 回退 v13**。
- ③ 微 case：fp16 D<=384 对齐且本核行数<=16 时改走逐行 ProcessTile（跳过 batch prep/Gather）
  → 本地热循环 dev_avg 无变化（[4,64] 5.75 vs 5.62、[16,64] 6.14 vs ~5.9）；msprof 单发微 case
  Task~11µs 中 vec/mte2/mte3 合计占比 <0.15 → 该尺寸已被 launch/task 固定开销主导。
  → **#1(#2/#3) 的差距不在 group0**（该尺寸走 group1 batch：aligned 且 64<=D<=32768），也不在
  批量 Init，而是框架 launch/入口固定开销；kernel 内改动本地无法测量到收益。
- 结论（后续方向）：#11/#13 若要再降只能走“GM 流量 5 pass→3 pass + 真重叠”的块级单读管线
  （需容忍 fp16 存 y 的精度风险或为 fp32 找到 128KB/行 UB 预算外的方案）；#8/#14 类为 vec/
  scalar 双饱和（1M 行 D64 msprof：vec 0.49/scalar 0.44/mte2 0.11），需 V 指令数与发射开销
  一起降。v14 未改动 kernel，等待下一次有正收益的合入再提交官方。

## (2026-09-09/10) — #1 为什么慢：官方口径对齐分析 + 微 case 暖队列 sweep（kernel 未改）
- 背景：用户问“#1 为什么比最优慢 ~4.5x、是不是没和官方对齐”。本轮本地又测了 bufCap
  （InitBuffer 按实际行数收缩）实验：fp16 [16,64] 7.38µs vs v13 的 5.6~6.1µs（旧口径），
  且 msprof 单发 micro Task≈11.1µs 无变化 → 无收益，`git checkout` 回退 v13，kernel 零改动。
- 新增工具 `bench_multi.asc`（同一进程顺序多 case、每 case 5 次预热 + 500 次连续入队、
  evStart/evEnd 事件计时），用于做微 case 形状扫描并贴近官方“连续多轮取均值”的口径。
  本地 910B3 扫描（dev_avg_us，500 次，命令见下）：
  ```
  cd build && ASCEND_VISIBLE_DEVICES=2 ARNBS_TIMES=500 ./bench_multi <各case根目录…>
  ```
  D=64 时各 dtype 的 dev_avg_us（行数 1/2/4/8/16/32/64/128/256/512/1024/2048/4096/8192）：
  | 行数 | fp16 | fp32 | bf16 |
  |--|--|--|--|
  | 1~32 | 3.1~3.5 | 3.2~3.4 | 3.1~3.3 |
  | 64~256 | **7.0~7.1** | 3.6~4.0 | **7.0~7.1** |
  | 512 | 4.58 | 4.42 | 4.54 |
  | 1024 | 5.49 | 5.43 | 5.48 |
  | 2048 | 7.50 | 7.38 | 7.57 |
  | 4096 | 11.7 | 11.7 | 11.7 |
  | 8192 | 15.4 | 20.4 | 15.5 |
  fp16 D=96/128/192/256 的行数 sweep：r1~r16≈3.3~3.5（floor）；r64~r256 D96=6.8~7.0、
  D128=4.8、D192=5.5~5.8、D256=3.9~4.6。D=512/1024/2048/4096 fp16 r1~r64≈3.3~5.3。
- 结论：
  1. 官方 #1 历次 4.25~6.9µs 与我们暖队列里 **fp16/bf16 D=64、rows 64~256 的 7.0µs 平台**
     同量级，最可能是官方 #1 的候选；但它不唯一（D=96 小行数也 6.8~7.0），且无法解释
     v3 时代的 4.25µs 与 v8 后 6.3~6.9µs 的 +2.4µs 差（部分来自后加的批量 Init），
     所以精确 shape 仍未钉死 → 与官方只能说“量级对齐”，不能说“逐位对齐”。
  2. #1 走 group1 批量路径（对齐 64<=D<=32768），不是 group0；v14③ 里“#1 不归 group0”成立。
  3. 慢的根因是**每次 launch 的固定开销**而非算力：msprof 单发微 case Task≈11µs 中
     vec 3% / mte2 9% / mte3 3% / scalar 29%，真正数据/计算不足 15%。暖队列口径下我们
     微 case floor ≈3.2µs，而榜单最优 #1 只有 1.47µs → 暖态 kernel 本体仍可再砍 ~2µs+。
  4. fp16/bf16 D=64 rows 64~256 出现 7.0µs 平台而 fp32 同形只有 3.6~4.0µs：批量 Init 的
     repG/repB/off 逐行复制（每行 3 个 PipeBarrier<PIPE_V>）+ 大 tile 缓冲配置是高嫌疑。
  5. 方法论修正：微 case 优化不能只看 msprof 单发（冷 launch 8~11µs 吞掉一切）；应以
     bench_multi 的暖队列口径（3.2µs floor）为准，两者结论会打架（v14③ 用单发得出
     “kernel 内改动无收益”，暖口径下才有可测信号）。
- 下一步候选：#1~#3 类做“超微路径”（本核数据量小于 1~2 tile 时走极简 Init：去掉 rep 表/
  双缓冲/冗余 DataCopy，尽量少 barrier 的单 tile 流程），把暖态 floor 从 3.2µs 压向 ~2µs；
  该路径可直接用 bench_multi 的 r1~r64 D64/D96 fp16/bf16/fp32 做本地回归。
- **补充（2026-09-10）**：#1 的完整归因、本地测试规模盘点、以及"用 v5/v8/v9a 三个历史二进制
  按比值指纹反推官方 #1 shape"的实验方案，见 [NOTE_case1.md](./NOTE_case1.md)。

## v18（盲提交候选 2026-09-11）— 行数相关屏障折叠：rep 表倍增构造 + 归约/pass2 行间屏障合并

**动机**：把历史各版本"最好的部分"叠起来并未产生新东西（v17 已是累积式最优并集：v13/v15/v16/v17
全在，v9 的 UltraAll 与 v14 三路实验因实测为负已回退）。这一次改的是**v17 里唯一还能被公式化指出
的结构性浪费**——"与行数成正比"的屏障开销，它在 v4 时代并不存在（v4 的逐行 pass2 没有任何行间屏障）。

**改动（kernel.asc，四处，全部是同步折叠，不改任何数值语义）**

| 位置 | v17 行为 | v18 行为 |
|--|--|--|
| group1 `AddRmsNormBiasGroup::Init`（batch） | 逐行 3 条向量指令 + **3 个 PIPE_V 屏障/行**（D=64 → 96 行 = 288 个） | `BuildRepTables`：γ/β 铺行表**倍增构造**（log2(rows) 步，每步 1 个屏障）；rstd 的 Gather offset 表逐行 `Duplicate` 但整表只留 1 个屏障 → **288 个屏障 → ~9 个** |
| group2 `AddRmsNormBiasPad::Init`（batch） | 同上（行宽 rowPad_） | 同上 |
| group1/group2 `RowReduceTo64(g)` | 每行内逐级归约，**每级 1 个屏障/行** | 改成**级外层、行内层**（级内各行互不依赖）→ 屏障数 O(levels) 而非 O(rows×levels) |
| group1 `ProcessTile` / group2 `ProcessTile` pass2 | 逐行 `Muls`→屏障→`FusedMulAdd`→屏障→`Cast`（3 个屏障/行/列分块） | 按**操作外层、行内层**发指令（Muls 全行→1 屏障→FMA 全行→1 屏障→Cast 全行→1 屏障） |

的步与步之间、归约的级与级之间、pass2 的 Muls→FMA→Cast 之间）。被删掉的只是"行与行之间"那些本来
互不依赖的屏障。历史旁证：v4 的 `ProcessTile` 逐行 pass2 连行内 RAW 都没有屏障，且通过了官方精度校验

## v19（2026-09-11）— #1 固定成本手术：γ/β 往返并入第一个 tile + 去掉冗余 store drain

**依据**：v18 已把"与行数成正比"的工作全部收掉（rep 表倍增、归约级外层、pass2 操作外层），

~7µs 是**每核固定开销**：几段串行 GM 往返 + 全 drain。本版就只动这条链，不碰任何行相关逻辑。
group1 改动三处（group2/group3/group0 不动，避免扩大影响面）：

| 位置 | v18 行为 | v19 行为 |
|--|--|--|
| `AddRmsNormBiasGroup::Init`（`!wide_`） | `PIPE_ALL` → DataCopy γ,β → `PIPE_ALL` → cast →（batch）rep 表；第一个 tile 再 `PIPE_ALL` → DataCopy x,r → `PIPE_ALL` ⇒ **两段 GM 往返完全串行** | 四路 DataCopy（γ,β,x,r 的第一个 tile）背靠背发出 → **一次 `MTE2→V` 等待** → cast + rep 表；第一个 tile 标 `prefetched` 跳过自己的搬运 ⇒ 省掉一整段暴露的 GM 延迟 |
| `ProcessTileBatch` / `ProcessTile` | 每 tile 恒定 `PIPE_ALL` ×2 + 载入 | `prefetched` 时跳过载入与等待；后续 tile 保持原路径（多 tile 时该开销本就被摊薄） |
| `ProcessTileBatch` 尾部 / `StageAndStore` | 输出 DataCopy 后再 `PIPE_ALL`（等 store 落地） | 输出前用精确事件 `V→MTE3`；**去掉尾部 drain**（og_/wk_ 的跨 tile 复用已由下一 tile 顶部的 `PIPE_ALL` 保护；kernel 以未完成的 MTE3 结尾是 AscendC 常规写法） |

同时把 `MTE2→V`、`V→MTE3` 从全 drain 改成精确事件（`SyncMte2ToV` / `SyncVToMte3`）。

**预期**：单 tile case（#1 家族）少一段串行 GM 往返 + 一次 store drain ⇒ 7.05µs 量级 → 4.5~5.5µs 量级；

## v20（2026-09-11，盲提交候选）— #1 家族切回逐行通路（批量 pass2 的 O(rows) 固定开销的证伪实验）

> 这一版只改**一处路由判据**（group1 限定），目的是把 #1 长期停在 ~7µs 的归因用一次官方评测钉死，
> 而不是继续在同一段代码上做零点几个 µs 的手术。v19（载入合并 + 去掉尾部 drain）保留在本 commit 内。

### 一、推导链（为什么怀疑“批量 pass2”）

1. 官方 #1 的历史最好 **4.25µs（v3/1cef497）/ 4.34µs（v5/e55cd65）** 出现在 group1 还**只有逐行 pass2**
   的年代：整 tile 载入 → 整 tile `y=x+r`、`sq=y²` → 每行 `WholeReduceSum` → 一次 `V_S` →
   **每行** `Muls(rstd) + FusedMulAdd(γ,β)` → 整 tile 写回。全程**没有 repG_/repB_ 铺行表、没有 Gather**。
2. v7（a4e88d6）引入批量 pass2（γ/β 铺行表 + `Gather` 展开 rstd + 整 tile FMA）后，官方 #1 从
   **4.34 → 10.88µs**；v9a 把铺表行数按本核裁剪 → 6.55µs；v18 把铺表从 O(rows) 个屏障降到
   O(log rows) → **#1 纹丝不动（7.12→7.05µs）**。
   ⇒ 这条链的固定开销（铺行表 + rstd 索引表 + Gather）**一直在**，被削了三次都没削到 #1 的落点。
3. v17 的“微 tile 退回逐行”门限是 `rowCount_ * D_ < 1536`：D=64 时只覆盖**本核 ≤ 24 行**。
   而官方 #1 的用时可反推本核行数：本地 D=64 的 marginal 模型 `t ≈ 3.2µs(floor) + 75ns × 本核行数`
   （由 13/26/52 行/核 = 4.58/5.49/7.50µs 三点拟合），官方 **7.05µs ⇔ 本核约 51 行**。
   ⇒ **旧门限差了一倍多，v17 的路由实验其实没覆盖 #1**。
4. 结论：v20 把判据从“本核元素数”换成“**本核行数**”，`MICRO_ROWS = 96`：
   - 本核 ≤ 96 行的 fp16/bf16 对齐小 D case（#1 家族）→ 逐行 `ProcessTile`（v5 结构 + v18 屏障折叠 + v19 预取）；
   - 本核 > 96 行（#8/#9/#10/#14 这类海量行）→ 仍走批量通路（那里 rep 表/Gather 能摊薄，v7 实测 4M×64 有 2.6x）。

### 二、结论

1. **H1 被证伪：#1 的 7µs 不是“批量 pass2 的固定开销”。**
   v20 把本核 ≤96 行的 fp16/bf16 对齐小 D 全部切到逐行通路（无 rep 表、无 Gather、无 rstd 索引表），
   #1 只动了 0.03µs（-0.4%，远在噪声内）。结合 v18（屏障折叠，-0.07µs）、v19（载入合并，含在本版内，
   同样没碰到 #1），**在 v9a 之后，对 group1 通路的任何改动都没能让 #1 移动一个可测的量**。
2. **v19 的载入合并是真的**：#2 -7.4%、#3 -12.4%，且 **#3 = 4.17µs 是历史最好**
   （v5 时代 4.64、v12 4.61、v17 4.54、v18 4.76）。#2/#3 这两个点用本地模型反推本核仅几行~十几行，
   本来就在 v17 的门限内走逐行通路 ⇒ 它们的收益只能来自 v19（γ/β 与第一个 tile 的 x/r 合并成一次
   GM 往返 + 去掉尾部 store drain），**不是** v20 的路由。
3. v20 的路由改动**没有在任何一个点上产生可测收益**（#4~#10 全在 ±3% 内，其中 #5 +3.0% 是唯一像样的
   负值，但 0.55µs 在 18µs 量级的点上也可能是噪声）。⇒ 该改动可以保留（无副作用、少一张 O(rows) 表），
   但不构成 #1 的解法。
4. 全表：12/15 变快或持平，1 点（#5）需观察，0 点真回退；均分 +0.89。

### 三、#1 的“已排除”清单（这是本轮最大的收获）

把 #1 至今没反应过的手段排开，它的 ~3.5µs“地板之上”部分不在下面任何一处：

| 已被排除的机制 | 由哪一轮证伪 |
|--|--|
| 批量 pass2 的 rep 表 / rstd 索引表 / Gather 展开 | **v20**（切到逐行后 #1 不动） |
| O(rows) 的 Init 屏障（倍增折叠） | v18（-0.07µs） |
| 第一个 tile 的 γ/β 串行往返 + 尾部 store drain | v19（含在 v20 提交内，#1 不动） |
| 行相关的归约/屏障（级外层、操作外层） | v18 |
| 空 block 的 Init（40 block 里尾部空 block 拖慢全体） | v15 / v16 / v17 |
| 本核行数被固定成整 tile（96 行） | v9a（唯一一次真的把 #1 拉动了 4.3µs） |

**剩下的可能性（按可疑度）**：

1. **#1 根本不在 group1 的 `!wide_` 家族里**（例如 `wide_`：2048 < D ≤ 32768）。
   证据：v19 的载入合并对**所有** `rowCount_ > 0 && !wide_` 的 group1 case 生效，而它明明让 #2/#3
   动了 7~12% —— 如果 #1 也在这条分支上，至少应该动一点。v19/v20 都没碰 wide 通路的 γ/β 往返，
   而 wide 通路每播一个 tile 就要重新 `LoadGBC` 一次（每个 2048 列分块两路 DataCopy + 两个 PIPE_ALL），
   微 case（例如 1 行 × D=4096/8192）会被这条串行链吃掉好几微秒。
   → 与 v3/v5 的 4.25/4.34µs 冲突（那一轮的好成绩要求 #1 落在 D%64==0 且 D≤512 的 gate 内），
   所以这条假设必须用实验判定，不能靠推理。
2. **启动/固定开销随内核规模变化**：v5 时代的 kernel 只有 2 条通路、10 个 InitBuffer；现在是 4 个 class ×
   3 种 dtype、13~17 个 InitBuffer、外加 ultra 双缓冲。微 case 上“执行不到但仍在二进制里”的代码、
   UB 申请数量、分支深度都可能进入 boot 路径。v3/v5 之后我们再没回到过那个体量。
3. #1 的 4.25/4.34µs 时代**不可复现**（v8 的 10.88µs 是异常值、其余都在 6.5~7.1µs 徘徊）。
   若如此，则不存在“回归”，只有“固定开销比榜首高一倍”这一个事实。

   支持该读法的两条旁证：① v9a 自己的 msprof 表显示那次“rep 表按本核行数裁剪”在微 case 上只值
   **-0.16 ~ -0.6µs**（`[1,64]` 8.12→7.96、`[16,64]` 8.36→7.80、`[256,64]` 8.46→7.86），
   而官方回贴里 #1 却“涨”了 4.3µs（10.88→6.55）——两者差 7 倍，只能解释为 v8 那次的 #1 是异常值；
   ② v8 那轮其它 14 点与 v5 基本持平（#8 67.64、#11 434.2、#12 133.3、#13 1.20ms），
   只有 #1 单独跳到 10.88µs，不像全局环境问题、更像单点扰动。
