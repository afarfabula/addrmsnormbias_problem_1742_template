> 目的：把每一次 `git commit` 对应的精度与性能测试结果固定下来，方便回溯与对比。
>
> 约定：
> - 本地核时（`dev_avg_us`）：`cd build && ASCEND_VISIBLE_DEVICES=3 ARNBS_NOSYNC=1 ARNBS_TIMES=300 ./add_rms_norm_bias_custom`

## v4 — 放宽分组路径：对齐行 D≤2048 全量走 tile/WholeReduceSum

  为按 D 动态分配；行内平方和折叠支持非 64 整数倍的尾部窗口（D=96/1152/1536 等），

## v5（提交将产生）— 大宽行统一进 group：γ/β 列分块流式 + 整行树形归约
- 内容：把 `AddRmsNormBiasGroup` 适用范围从 D<=2048 扩到 fp16/bf16 D<=8192、
  fp32 D<=4096（对齐行）。D>2048 时 γ/β 不再整行常驻，改为按 2048 列分块
  流式加载/转 fp32 后逐行 FMA（行数据 fp32 只存一份，不再像旧路径 pass2
  二次读 GM）；行内平方和从“逐 64-lane 串行折叠”改成整行 log 深度树形归约
  （非 2 幂先折尾部，再逐级减半到 64 lane），消除 D/64 长度的依赖链。
- 精度：`run_accuracy.py` 16/16 PASS；宽 D 抽样 15 个（fp16/fp32/bf16，
  D=2304/4096/8192，rows 16~8192，含 3D/4D）全部 frac<=6e-6。

## v6（提交将产生）— 非对齐行 padded-tile 路径（D=100/104/136...）
- 内容：新增 `AddRmsNormBiasPad`：行首在 GM/UB 非 32B 对齐（fp16/bf16 D%16!=0、
  fp32 D%8!=0）时，行在 UB 内按 rowPad=align64(D) 对齐存放并在 GM 侧逐行
  DataCopyPad 读写（行尾用 rightPadding 显式补 0，避免 32B 块写入污染 pad 位）；
  向量/归约全在 padded 空间进行，γ/β 同法补零。取代旧逐行 legacy（其逐行
  sync/密集小指令造成 D=100 类慢 3~5x）。
- 精度：`run_accuracy.py` 16/16 ALL PASSED（含 fp16/fp32 D=100）；rows=1/4 D=100
  逐位 0 误差复验；修复过程详见 git 记录（rightPadding 语义为 dst 尾块补 0）。

## v7（已提交 a4e88d6，已推送）— fp16/bf16 小 D 批量 pass2 + repeat 批量归约 + 超宽行窗口化
- 内容：
  - **批量 WholeReduceSum**：每 tile 128 次独立 64->1 硬件归约合成一次
    `repeat=g` 的指令（实测该归约在 c220 把每行结果写到**连续**元素，非 8-lane 间隔）；
  - **fp16/bf16 D<=384 对齐行批量 pass2**：γ/β 在 Init 复制成整 tile（fp32 行内复制），
    rstd 用 Gather（offset 单位为**字节**）在 vector 域展开，替代每行 GetValue +
    逐行 Muls/FMA/Cast（旧路径 ~4 短向量指令/行 → ~5 条整 tile 大向量指令）；
    tile 上限 6144 元素（D=64 -> 96 行/tile）。
  - **超宽对齐行窗口化（group 内 ultra_）**：fp16/bf16 D>8192、fp32 D>4096（上限
    32768/16384）时，按 GT_ELEMS 宽窗口两次读 x/residual：pass1 逐窗口折 sq 进
    64-lane acc -> rstd；pass2 逐窗口重读并按 PARAM_STRIPE 应用 γ/β。
  - host 对齐 gate 上限提升：fp16/bf16 D<=32768、fp32 D<=16384。
- 精度：`run_accuracy.py` 16/16 ALL PASSED；`run_heavy_accuracy.py` 13/13 PASS；
  超宽行独立 8 组（fp16 D=16384/32768、fp32 D=8192/16384 × 多行数）vs golden 全 PASS。
- msprof（310B, dev_avg, reps=300）：

## v13（本轮提交）— Pad 批量 pass2（非对齐小/中 D 行密集）
- 背景：非对齐小/中 D（Pad 路径，D<=2048）在行密集时明显落后对齐路径：fp16 [8192,100]=49µs vs
  对齐 [8192,96]=27µs（1.8x）。原 Pad ProcessTile 每行独立 WholeReduceSum + 每行 GetValue 标量读 +
  短向量 FMA，逐行往返太多。
- 改动（AddRmsNormBiasPad，fp16/bf16 生效，fp32 保底不变）：
  - tile 元素预算压到 BATCH_TILE=6144（capRows=6144/rowPad），Init 时把 γ/β 按行复制成 repG_/repB_
    并生成 Gather offset 表 off_（tile 内行号从 0 计，所有 tile 复用）；
  - 新增 ProcessTilePadBatch：整 tile 一次 DataCopyPad 行载 → 整 tile fp32 sq → RowReduceTo64 →
    **单次 WholeReduceSum(repeat=g, 行距 rowPad/8)** → rstd 批量向量 → Gather 展开 → 整 tile
    Mul + FusedMulAdd → 整 tile Cast → 逐行精确写回。无逐行归约/标量同步。
- 精度：run_accuracy 16/16、heavy 13/13；pad 专项 10/10（fp16/bf16，D=100/104/108/136/2044、
  3D/1M 行）。PadWide/group1 未动。
- 本地性能（dev_avg_us，reps=100，同机）：

- 尝试未果：把 group 批量（D<=384）放宽到 D<=1536 覆盖 #8 类中等 D → 实测反而变差（

## (v14 实验期 2026-09-09) — 三路候选改造的本地测量与结论（未合入）
- 背景：官方 v12=39.56/#11-272µs/#13-776µs 后，测试了 ①PadWide 单读 y-hold、②PadWide 块级
  两阶段 UltraPadAll、③微 case 小行数路由，全部**未达合入标准**，kernel 保持 v13 原样。
- ① 单读 y-hold（fp16 行 y 以 fp16 常驻 64KB / fp32 128KB，pass2 不回读 GM x/residual）：
  - 精度：fp32/fp16 非对齐宽行 vs numpy golden 全 PASS（fp32 maxdiff 9.5e-7、fp16 2.0e-3，
    bf16 为既有 ~2ULP 量级差异）；但行尾 γ 非对齐 DataCopy 会错最后 4 列（已定位修复）。
  - 性能（v13 per-row -> hold）：fp16 [1024,32760] 368→370（≈）、[2048,32760] 747→777（≈）；
    fp32 [512,32764] 240→404（+68%）、[1536,32764] 797→1404（+76%）——fp32 反而显著回退。
    msprof（fp32 [2048,32764]）：mte3 0.126→0.240、scalar 0.269 上关键路径；GM 流量下降但
    UB 内 y 往返与更小窗口的向量/同步开销吃掉收益。
  - 另注意：历史 v9 记录曾提示 fp16 y 缓存会让 ~0.7% 元素超 1e-3 官方阈值（vs torch golden），
    本方案精度上也有同类风险 → **弃用**。
- ② PadWide 块级两阶段 UltraPadAll（行密集 G=8：pass1 逐行 WholeReduceSum->sum_[r]，整块批量
  rstd 一次 V_S/S2V；pass2 列 stripe(2048) 外循环/行内扫、γ/β 每 stripe 块内只读一次）：
  - 精度：fp16/fp32/bf16 宽行专项全 PASS（与 v13 逐位一致量级）。
  - 性能（v13 per-row -> UltraPadAll）：fp16 [512,32760] 186→185（≈）、[1024] 368→384（+4%）、
    [2048,32760] 747→865（**+16% 回退**）；fp32 [512,32764] 240→210（-12%）、[1024] 547→588、
    [1536] 797→861、[2048] 1064→1149（+8%）。
  - 与 group1 对齐 UltraAll（v9，对齐宽行 -13~22%）结论相反：pad 宽行 stripe-outer 行扫把每行
    读切成多个 2048 段、跨 40 核交错，破坏了大行连续读的 GM 局部性；fp32[512] 的 -12% 是少数
    例外 → **弃用，kernel 回退 v13**。
- ③ 微 case：fp16 D<=384 对齐且本核行数<=16 时改走逐行 ProcessTile（跳过 batch prep/Gather）
  → 本地热循环 dev_avg 无变化（[4,64] 5.75 vs 5.62、[16,64] 6.14 vs ~5.9）；msprof 单发微 case
  Task~11µs 中 vec/mte2/mte3 合计占比 <0.15 → 该尺寸已被 launch/task 固定开销主导。
  → **#1(#2/#3) 的差距不在 group0**（该尺寸走 group1 batch：aligned 且 64<=D<=32768），也不在
  批量 Init，而是框架 launch/入口固定开销；kernel 内改动本地无法测量到收益。
- 结论（后续方向）：#11/#13 若要再降只能走“GM 流量 5 pass→3 pass + 真重叠”的块级单读管线
  （需容忍 fp16 存 y 的精度风险或为 fp32 找到 128KB/行 UB 预算外的方案）；#8/#14 类为 vec/
  scalar 双饱和（1M 行 D64 msprof：vec 0.49/scalar 0.44/mte2 0.11），需 V 指令数与发射开销
  一起降。v14 未改动 kernel，等待下一次有正收益的合入再提交官方。

## (2026-09-09/10) — #1 为什么慢：官方口径对齐分析 + 微 case 暖队列 sweep（kernel 未改）
- 背景：用户问“#1 为什么比最优慢 ~4.5x、是不是没和官方对齐”。本轮本地又测了 bufCap
  （InitBuffer 按实际行数收缩）实验：fp16 [16,64] 7.38µs vs v13 的 5.6~6.1µs（旧口径），
  且 msprof 单发 micro Task≈11.1µs 无变化 → 无收益，`git checkout` 回退 v13，kernel 零改动。
- 新增工具 `bench_multi.asc`（同一进程顺序多 case、每 case 5 次预热 + 500 次连续入队、
  evStart/evEnd 事件计时），用于做微 case 形状扫描并贴近官方“连续多轮取均值”的口径。
  本地 910B3 扫描（dev_avg_us，500 次，命令见下）：
  ```
  cd build && ASCEND_VISIBLE_DEVICES=2 ARNBS_TIMES=500 ./bench_multi <各case根目录…>
  ```
  D=64 时各 dtype 的 dev_avg_us（行数 1/2/4/8/16/32/64/128/256/512/1024/2048/4096/8192）：
  | 行数 | fp16 | fp32 | bf16 |
  |--|--|--|--|
  | 1~32 | 3.1~3.5 | 3.2~3.4 | 3.1~3.3 |
  | 64~256 | **7.0~7.1** | 3.6~4.0 | **7.0~7.1** |
  | 512 | 4.58 | 4.42 | 4.54 |
  | 1024 | 5.49 | 5.43 | 5.48 |
  | 2048 | 7.50 | 7.38 | 7.57 |
  | 4096 | 11.7 | 11.7 | 11.7 |
  | 8192 | 15.4 | 20.4 | 15.5 |
  fp16 D=96/128/192/256 的行数 sweep：r1~r16≈3.3~3.5（floor）；r64~r256 D96=6.8~7.0、
  D128=4.8、D192=5.5~5.8、D256=3.9~4.6。D=512/1024/2048/4096 fp16 r1~r64≈3.3~5.3。
- 结论：
  1. 官方 #1 历次 4.25~6.9µs 与我们暖队列里 **fp16/bf16 D=64、rows 64~256 的 7.0µs 平台**
     同量级，最可能是官方 #1 的候选；但它不唯一（D=96 小行数也 6.8~7.0），且无法解释
     v3 时代的 4.25µs 与 v8 后 6.3~6.9µs 的 +2.4µs 差（部分来自后加的批量 Init），
     所以精确 shape 仍未钉死 → 与官方只能说“量级对齐”，不能说“逐位对齐”。
  2. #1 走 group1 批量路径（对齐 64<=D<=32768），不是 group0；v14③ 里“#1 不归 group0”成立。
  3. 慢的根因是**每次 launch 的固定开销**而非算力：msprof 单发微 case Task≈11µs 中
     vec 3% / mte2 9% / mte3 3% / scalar 29%，真正数据/计算不足 15%。暖队列口径下我们
     微 case floor ≈3.2µs，而榜单最优 #1 只有 1.47µs → 暖态 kernel 本体仍可再砍 ~2µs+。
  4. fp16/bf16 D=64 rows 64~256 出现 7.0µs 平台而 fp32 同形只有 3.6~4.0µs：批量 Init 的
     repG/repB/off 逐行复制（每行 3 个 PipeBarrier<PIPE_V>）+ 大 tile 缓冲配置是高嫌疑。
  5. 方法论修正：微 case 优化不能只看 msprof 单发（冷 launch 8~11µs 吞掉一切）；应以
     bench_multi 的暖队列口径（3.2µs floor）为准，两者结论会打架（v14③ 用单发得出
     “kernel 内改动无收益”，暖口径下才有可测信号）。
- 下一步候选：#1~#3 类做“超微路径”（本核数据量小于 1~2 tile 时走极简 Init：去掉 rep 表/
  双缓冲/冗余 DataCopy，尽量少 barrier 的单 tile 流程），把暖态 floor 从 3.2µs 压向 ~2µs；
  该路径可直接用 bench_multi 的 r1~r64 D64/D96 fp16/bf16/fp32 做本地回归。

## v15（2026-09-10）— group1 空 block 跳过 γ/β+rep 表构建（微/中行数平台修复）
- 背景：本地微 case sweep 发现 fp16/bf16 D64 rows 64~256 出现 ~7.0µs 平台（同形状 fp32 仅
  3.6~4.0µs）。根因：host 固定启动 40 个 block，总行数不足 40×blockRows 时尾部 core 分到
  rowCount=0 的空 block；但 Init 里 `rowsPerTile_` 裁剪带 `rowCount_>0 &&` 守卫，空 block 的
  rowsPerTile_ 仍为整 tile（D64 -> 96 行），于是空 block 也要跑完整 γ/β 载入 + 96 行
  repG/repB/off 表构建（96×3 = 288 个 PipeBarrier<PIPE_V>），空 block 反而成为 kernel 关键路径。
- 改动（kernel.asc，仅 AddRmsNormBiasGroup::Init）：γ/β 整行载入+ToFp32+批量 rep 表构建整体
  包进 `if (rowCount_ > 0 && !wide_)`；空 block 保留 InitBuffer（编译器/UB 分配前提）但不再做
  任何设备侧 γ/β/rep 工作。其余代码路径不变。
- 精度：run_accuracy 16/16、run_heavy_accuracy 13/13 全 PASS。
- 本地热队列 dev_avg_us（v13 -> v15，bench_multi，500 次）：
  | shape | v13 | v15 | 变化 |
  |--|--|--|--|
  | fp16 [64,64] | 7.09 | 3.85 | -46% |
  | fp16 [128,64] | 7.04 | 4.04 | -43% |
  | fp16 [256,64] | 7.09 | 4.28 | -40% |
  | bf16 [64,64] | 7.06 | 3.83 | -46% |
  | fp16 [64,96] | 6.95 | 4.68 | -33% |
  | fp16 [64,128] | 4.85 | 3.96 | -18% |
  | r1~r32 D64 与 r512+ D64 | ≈ | ≈ | ±5%（噪声） |
- 备注：该 7µs 平台与官方 #1 的 6.3~6.9µs 同量级，若 #1 属 D64/D96 中行数 fp16/bf16，本修复
  有望直接把 #1 拉到 ~4µs；group2(Pad) Init 存在同类空 block 开销（下一步同样处理）。
