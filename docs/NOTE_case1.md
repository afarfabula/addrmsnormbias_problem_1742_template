# Case #1 专项分析（comment）：为什么一直做不好 + shape 反推实验方案

> 用途：把 #1 的长期归因、本地测试规模盘点、以及"用三个历史版本的二进制反推出官方 #1
> 真实 shape"的实验方案固定下来。本文只做分析与计划，不改 kernel。
> 关联：[RESULTS.md](./RESULTS.md)（正式成绩/精度记录）。

## 0. 摘要

- 官方 #1 历史最好 **4.25µs**（v3/v4 期），现状 **7.12µs**（v17），我们自己比历史最好差 1.7x；
  离榜单最优 1.47µs 是 4.84x，是 15 点里离最优最远的一个。
- 根因**不在算子计算**：msprof 单发微 case Task≈11µs，其中 vec 3% / mte2 9% / mte3 3%，
  真正数据搬运+计算 <15%，其余是 launch / Init / 同步的固定开销。
- 但我们**无法在本地复现官方那个量**：单发 msprof 8~11µs、暖队列 floor 3.2µs、官方 4.25~6.9µs，
  三套口径互相打架 → 本地优化收益无法预测官方结果（v15~v17 已实证：本地 7.0→3.85µs，官方不动）。
- 因此顺序应当反过来：**先反推官方 #1 的 shape，再谈优化**。反推手段见第 5 节。
- **2026-09-10 更新**：候选空间已从“完全未知”收敛到 **fp16/bf16 × D∈{64,128,192,256,320,384}**
  （12 种组合），并推断本核行数落在 25~96 档——**恰好是 v9a/v14/v15/v16/v17 五次修复都没覆盖的
  盲区**。完整推导见第 8 节。

## 1. 官方成绩轨迹（#1）

| 版本（commit） | #1 官方用时 | 榜单最优 | 倍数 | 备注 |
|--|--|--|--|--|
| 6ec695b | 6.88µs | 1.47µs | 4.68x | tiling 缓存修复期 |
| v3/v4（1cef497） | **4.25µs** | 1.47µs | 2.89x | 批量行分组 + WholeReduceSum，**历史最好** |

#1 确实走 group1（分组/批量路径），shape 属于"对齐小 D"族。

## 2. 为什么一直做不好（归因）

### 2.1 瓶颈不在计算
msprof 单发微 case Task≈11µs：vec 3% / mte2 9% / mte3 3% / scalar 29%，数据+计算合计 <15%。
优化搬运/向量通路对 #1 天然无效——这是它在所有版本里都最迟钝的根本原因。

### 2.2 我们的结构固定成本高
kernel 里每条路径的 `InitBuffer` 调用数（微 case 上与数据量无关的纯开销）：

| 路径 | InitBuffer 数 |
|--|--|
| group0（保底） | 14 |
| group1（对齐行，含 batch/ultra） | **17** |
| group2（Pad） | 14 |
| group3（PadWide） | 13 |

再叠加：从 GM 读 tiling、集团分派、几十处 `PipeBarrier`。微 case 上这些就是全部成本。
v14 的 bufCap 实验（按实际行数收缩 InitBuffer）本地反而更差（7.38 vs 5.6~6.1µs），已回退。

### 2.3 shape 至今没钉死
唯一证据是**量级对齐**：本地 fp16/bf16 D=64、rows 64~256 有 7.0µs 平台，官方 #1 是 4.25~6.9µs。
但该平台不唯一（D=96 小行数也是 6.8~7.0µs），也解释不了 v3 的 4.25µs 与 v8 后 6.3~6.9µs 的 +2.4µs 差。
（注：该结论已在 2026-09-10 大幅推进——#1 的 dtype/D 已可锁定，见第 8 节。）

### 2.4 三套测量口径矛盾

| 口径 | 微 case 数值 | 问题 |
|--|--|--|
| msprof 冷单发 | 8~11µs | 冷启动吞掉一切信号（v14③ 据此得出"无收益"的错误结论） |
| bench_multi 暖队列 | floor ≈3.2µs | 与官方 4.25~6.9µs 不同量级 |
| 官方 | 4.25~6.9µs | 无法在本地复现 |

实证反例：v15/v16/v17 本地把 fp16 [64,64] 7.09→3.85µs、D=100 fp16 12.9→4.5µs，
官方 #1/#4~#7 完全不动。

### 2.5 最优值低于我们的暖态 floor
榜单最优 #1 = 1.47µs，比我们暖队列 floor（3.2µs）还低 2.2x。这暗示榜首不是"把同一条 kernel
优化得更好"，而可能换了执行形态（极简 micro kernel，或 host 侧开销占比完全不同）。

## 3. 两个待验证假设

- **H1（40 整数倍假设）**：v15~v17 修的是"空 block"——只当 `totalRows` 不能被
  `ceil(totalRows/40)` 整除时才出现（40 = 本机 vector core 数）。若官方 #1 的行数恰是 40 的
  整数倍（如 80 / 160 / 320），则 40 个 block 个个有行，**v15~v17 对它完全无效**——可解释
  "本地 [64,64] 大改、官方 #1 不动"。验证方式：在 shape 网格里显式标注 40 的整数倍与附近的点。
- **H2（host 口径假设）**：若官方计时包含 host 侧（tiling 构造 + `<<<>>>` launch），而我们
  bench_multi 报的是 dev 事件时间，则关键路径不在 kernel 内，微 case 优化方向应从 kernel Init
  转向 host 侧。验证方式：同一批 shape 用 `wall_avg_us` 而非 `dev_avg_us` 重做第 5 节的匹配
  （main.asc 的 `[KERNTIME]` 同时打印两者）。

| 层级 | 规模 | 说明 |
|--|--|--|

投入不小，问题在于其中没有一个是"已确认就是官方 #1"的——这正是第 5 节要解决的。

## 5. 反推官方 #1 shape 的实验方案（核心）

### 5.1 原理
官方对同一个 shape 在三个版本上给过三个数：**4.34µs(v5) → 10.88µs(v8) → 6.55µs(v9a)**。
即官方口径下该 shape 先劣化 2.51x、再恢复 0.60x。这个"劣化-恢复指纹"是 shape 无关的比值，
可以用本地二进制复现：对每个候选 shape s，用三个版本的二进制各测一次，算

```
r1(s) = t_v8(s)  / t_v5(s)     目标 ≈ 2.51
r2(s) = t_v9a(s) / t_v8(s)     目标 ≈ 0.60
```

同时匹配 r1、r2 的 shape（族）即官方 #1。**关键在于比值而非绝对值**——绝对值受口径影响，
比值在同一次本地会话内是可比的。

### 5.2 准备三个二进制
```bash
AR=/home/quyanyi/addrmsnormbias_problem_1742_template
for rev in e55cd65 a168ae2 0ed5986; do
  git -C "$AR" worktree add /tmp/arnb_$rev $rev
  (cd /tmp/arnb_$rev && ./run.sh)   # 或只到 make 步骤，不必跑默认 case
done
```
注意：旧 revision 没有 `bench_multi.asc`（fe9069e 才加）。两种做法：
① 把当前的 `bench_multi.asc` + CMake 目标拷进旧 worktree（case.bin 格式未变）；
② 直接用旧 worktree 的 `add_rms_norm_bias_custom`（main.asc 已支持
`ARNBS_TIMES` / `ARNBS_NOSYNC`，`[KERNTIME]` 同时打印 dev 与 wall 两个数）。

### 5.3 shape 网格（重点在 group1 对齐小 D）
前提是同一次会话内三个二进制**交错**跑同一批 case（避免频率漂移）：

| 维度 | 取值 |
|--|--|
| dtype | fp16 / bf16 / fp32 |
| D | 64 / 96 / 128 / 192 / 256 / 384（对齐，走 group1 batch） |
| rows | 40 / 64 / 80 / 96 / 120 / 128 / 160 / 192 / 256 / 512 / 1024 |
| 标注 | rows 为 40 的整数倍的点 → 用于验证 H1 |

**2026-09-10 更新**：据第 8 节的收敛结果，第一轮只需覆盖
`fp16/bf16 × D∈{64,128,192,256,320,384} × rows∈{512,1024,2048,3072,4096}`（2×6×5 = 60 点），
并把 rows=40 的整数倍单独标注用于验证 H1；D=96/320 这类"非常见但可能"的值也一并覆盖。

（rows 只需覆盖到能区分 batch 与非 batch 行为的区间；D>384 的候选可在第二轮加。）

### 5.4 执行
```bash
# 对每个 rev 的 build 目录，对同一批 case root 跑 500 次取 dev_avg_us
cd /tmp/arnb_e55cd65/build && ARNBS_TIMES=500 ./bench_multi <case根目录…>
cd /tmp/arnb_a168ae2/build && ARNBS_TIMES=500 ./bench_multi <case根目录…>
cd /tmp/arnb_0ed5986/build && ARNBS_TIMES=500 ./bench_multi <case根目录…>
```
前置缺口：需要一个小脚本批量生成 case 目录（每个 shape 一个 `input/{case,x,residual,gamma,bias}.bin`），
可基于 `scripts/bench_shape.py` 改造为批量版（建议新增 `scripts/gen_sweep.py`）。

### 5.5 判定
按 `|r1-2.51|/2.51 + |r2-0.60|/0.60` 升序排序，取 top-1 形状族。判据：误差 <15% 视为命中；
top-3 若落在同一 D/rows 邻域，同样可认为锁定。

### 5.6 失败分支
- **无 shape 命中** → 用 `wall_avg_us` 重做 5.1 的匹配，验证 H2（官方口径含 host 开销）；
  若 wall 口径下命中，则优化方向转为 host 侧（tiling 构造/缓冲池/launch）。
- **两套口径都不命中** → 官方 #1 的关键路径既不在我们 kernel 内、也不在我们能测的 host 段，
  需要向主办方确认计时口径，或放弃精修 #1、把资源转投 #11/#12。

## 6. 若反推成功：后续优化方向

- 命中形状若落在 group1 batch 路径：做"超微路径"（极简 Init：去掉 rep 表 / 双缓冲 / 冗余 DataCopy，
  单 tile 流程，最少 barrier），目标把暖态 floor 从 3.2µs 压向 ~2µs。
- 命中形状若与 40 的整数倍相关：说明空 block 不是它的瓶颈，应转向 InitBuffer 数量本身
  （合并 buffer、按路径裁剪 UB 预算）。
- 若 H2 成立（host 口径主导）：把优化从 device 侧移到 host 侧（tiling 结构体常驻、
  避免每 launch 重新填、减少 `aclrtMalloc`/H2D）。

## 7. 与现有结论的关系

- 本文不推翻 RESULTS.md 的结论，而是补上 #1 的归因与下一步实验设计；
- 优先级上，#1 仍排在有明确解法的 **#12 / #11** 之后（见 RESULTS.md 的「v17 官方评测」节）：

## 8. （2026-09-10 补充）候选空间收敛：从"完全未知"到 12 种组合

本节不依赖本地复现，而是利用**历史版本之间的行为差异**反推 #1 的形状——证据来自我们自己的
官方评测记录，因此不受本地口径问题影响。

### 8.1 证据 1：v3/v4 的分组门限 = `D % 64 == 0 && D <= 512`

`1cef497` 只做了一件事：**新增** `AddRmsNormBiasGroup`（217 行纯新增，`AddRmsNormBiasKernel`
完全未改动），当时 host 侧门限为：

```cpp
tiling.group = ((D % 64 == 0) && (D <= 512)) ? 1U : 0U;
```

而官方 #1 在该次评测中从 6.88µs 降到 4.25µs（-38%，远超噪声）。既然本次只开了这一条新通路、
且 #1 大幅受益，则 **#1 必然满足 `D % 64 == 0 && D <= 512`**。
（RESULTS.md 该节的小结也明确记着"只吃到 v3 分组路径的点（#1/#3/#8/#14）"。）

### 8.2 证据 2：v9a 的 6 行改动只能影响 batch 路径的 rep 表

`0ed5986`（v9a）的 kernel 改动只有这一段：

```cpp
if (rowCount_ > 0 && rowsPerTile_ > rowCount_) {
    rowsPerTile_ = rowCount_;
}
```

而 `rowsPerTile_` 全代码里唯一的实质用途是 **batch 路径 Init 中"按行铺 γ/β/rstd"的循环**
（非 batch 路径下裁剪它不改变实际工作量：tile 循环本来就取 `min(rowCount_, rowsPerTile_)`，
InitBuffer 尺寸用的是 `tileCap` 而非它）。该改动让 #1 从 10.88 → 6.55µs，因此 **#1 走 batch 路径**；
而 batch 的启用条件是 `sizeof(T) != 4 && !wide_ && D_ <= 384`。

### 8.3 收敛结果

| 维度 | 结论 | 把握 |
|--|--|--|
| dtype | fp16 或 bf16（**不是 fp32**） | 高 |
| D | 64 的整数倍且 ≤384 → **{64, 128, 192, 256, 320, 384}** | 高 |
| 路径 | group1 的 batch（rep 表 + Gather）通路 | 高 |
| 规模 | 微 case（单核有效数据仅几 KB） | 高 |
| rows | 本核行数约 **25~96** ⇒ 总行数约 2000~3600 | 中（推断） |
| 精确 D / rows / numDims | 未知 | — |

即 **(dtype, D) 只剩 12 种组合**。

### 8.4 定量模型：batch Init 的 O(行数) 成本

rep 表循环每行 3 个 `PipeBarrier<PIPE_V>`，成本 ≈ `3 × 行数 × ~20ns`：

- v7 原始版本（固定铺满 96 行）：`96 × 3 × 20ns ≈ 5.8µs` → 与 v8 实测退步 +6.5µs
  （4.34 → 10.88）吻合；
- v9a 之后（`min(96, 本核行数)`，取本核 52 行）：`52 × 3 × 20ns ≈ 3µs` → 与 10.88 → 6.55
  的恢复幅度（-4.3µs）同量级。

而同一核真正要算的数据（52 行 × 64 元素 × 2B ≈ 6.6KB）远小于这张表——**Init 比干活贵**。
这就是 #1 效果差的全部机制。

### 8.5 为什么五次修复都没命中

| 版本 | 修的是 | 对 #1 无效的原因 |
|--|--|--|
| v9a | rep 表从固定 96 行改为 `min(96, 本核行数)` | 有效（10.88→6.55），但成本仍是 O(本核行数) |
| v14③ | 本核行数 ≤16 时改走逐行 ProcessTile | #1 的行数远大于 16，够不着 |
| v15 / v16 | 空 block（`rowCount_ == 0`）跳过 Init | #1 的 40 个 block 个个有行，没有空 block |
| v17（host） | 只启动有行的 block | 对 #1 本来就是 40 个满载 block，无变化 |
| v17（路由） | 本核 `rowCount_ * D_ < 1536` 退回逐行 | D=64 时要求本核行数 <24；#1 在 25~96 之间 |

**盲区：所有修复覆盖了"本核行数 <24"与"存在空 block"两种情形，唯独漏掉 25~96 这一档。**
这正好解释了那个反直觉的观测——本地 `fp16 [64,64]` 被 v15~v17 从 7.09µs 修到 3.6µs（本核仅 2 行），
而官方 #1 从 6.69 → 7.12µs 纹丝不动：我们优化的是同族里行数极少的那个点，不是 #1。

### 8.6 可验证预测

- **预测 A（本地，零官方提交）**：用 v13 与 v17 两个二进制测 `fp16 [2048,64]` 与 `[4096,64]`。
  若两者用时几乎相同（都不受 v15~v17 影响），即坐实该盲区、也就坐实 #1 的档位。
- **预测 B（官方探测）**：用第 5 节的延时探测法，`delay = D µs` 一次提交即可读出各点 D，
  与上述 12 种组合比对即可锁定 #1；同理可读 rows 验证"本核 25~96 行"的推断。
- **预测 C（修复方向）**：若把 batch 的启用条件从 `rowCount_ * D_ < 1536` 改成
  "`rowsPerTile_` 被裁剪过（`rowCount_ < BATCH_CAP / D`）时退回逐行"，理论上可让 #1 回到 ~4.3µs。
  **但不可直接推**：v3/v4 时代本地 `fp16 [2048,64]` 曾测到 ~10.2µs（非 batch、不同测量口径），
  与现在 batch 路径的 7.5µs 不可直接比较。必须先对 8.3 的 12 组候选做本地 A/B，再决定是否改路由。
